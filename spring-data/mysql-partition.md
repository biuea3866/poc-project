# MySQL 파티셔닝 검증

RANGE 파티셔닝이 조회 성능에 실제로 어떤 영향을 주는지 쿼리 형태별로 측정한다.

> **1차 측정을 폐기하고 다시 측정했다.** 1차 결과("파티셔닝 적용 시 TPS 73% 증가")는 비교군의
> 인덱스 구조가 서로 달랐고, JOIN 이라고 적은 API 가 실제로는 쿼리 2회였으며, 두 비교군의 결과 집합도
> 달랐다. 결함 목록과 재설계 근거는 [scripts/rebench/PLAN.md](./scripts/rebench/PLAN.md) 에 있다.

## 실험 설계

### 데이터

상품 1,000만 건을 **세 벌** 만든다. 세 테이블은 완전히 같은 행을 담고, 인덱스도 같다.
비교군 사이에 남는 차이는 PK 폭과 파티셔닝 여부뿐이다.

| 테이블 | PK | 파티셔닝 | 역할 |
| --- | --- | --- | --- |
| `product` | `(id)` | 없음 | 대조군 |
| `product_composite_pk` | `(id, created_date)` | 없음 | PK 폭 변화만 분리 |
| `product_partitioned` | `(id, created_date)` | 연도별 RANGE 7개 | 실험군 |

세 테이블 모두 `idx_created_date`, `idx_category` 를 갖는다. 파티션 테이블에만 날짜 인덱스가
없던 1차 측정의 비대칭을 없앤 것이다.

댓글 2,000만 건은 파티션 테이블로 만들고, `created_date` 를 **해당 상품과 같은 해**로 맞춘다.
이래야 JOIN 에 댓글 날짜 조건을 더해도 결과 집합이 바뀌지 않고 프루닝만 켜고 끌 수 있다.

`created_date` 는 `id` 와 함께 증가한다(append-only). 주문·로그 같은 실제 시계열 테이블의 모양이고,
비파티션 테이블에서도 연도별 행이 클러스터드 인덱스상 인접하게 만들어 파티셔닝에 유리하도록
행을 흩뿌리지 않기 위한 선택이다.

데이터셋은 두 벌이다.

| 데이터셋 | 상품 분포 |
| --- | --- |
| `partition_uniform` | 2020~2025 각 166만 건 (균등) |
| `partition_skewed` | 2024 에 900만 건(90%), 나머지 5개 연도 각 20만 건 |

### 측정 프로토콜

엔드포인트 1개당 다음을 반복한다.

1. MySQL 컨테이너 재기동 → 버퍼 풀 초기화
2. 워밍업 40초 (커넥션 재수립 + 작업 집합 적재)
3. 본 측정 3회 — 50 VU 클로즈드 모델, think time 없음, 20s ramp → 40s steady → 10s down

표의 값은 3회 중앙값이고 괄호는 최소~최대다. **반복 간 변동폭이 두 비교군의 차이보다 크면
"차이 없음" 으로 읽는다.**

### 순서 효과 대조군

`docker restart` 는 InnoDB 버퍼 풀만 비우고 **호스트 OS 페이지 캐시는 남긴다.** 그래서 뒤에 도는
케이스일수록 유리해진다. 본 측정과 정반대 순서로 같은 케이스를 다시 돌려, 순위가 유지되는지 확인한다.

### 환경

- MySQL 8.0.46 (Docker), `innodb_buffer_pool_size=2G`
- 데이터 총량 약 7.4GB — 버퍼 풀의 3.7배라 I/O 바운드다
- k6 v1.4.0, Spring Boot 4.0.1 (JdbcTemplate 직접 호출)
- 로컬 macOS 단일 호스트. 앱·부하 생성기·DB 가 같은 머신에서 CPU 를 나눠 쓴다.

## 결과 — 균등 데이터셋

원본: [scripts/rebench/results/uniform/](./scripts/rebench/results/uniform/)

### 실험 A — 파티션 키를 포함한 범위 조회 (`LIMIT 100`)

```sql
SELECT id, name, created_date FROM <table>
WHERE created_date BETWEEN '2024-01-01' AND '2024-12-31'
ORDER BY created_date, id LIMIT 100;
```

세 테이블 모두 `idx_created_date` 레인지 스캔을 탄다. 파티션 테이블만 `p2024` 로 프루닝된다.

| 구성 | 본 측정 TPS | 역순 대조군 TPS |
| --- | --- | --- |
| 비파티션 PK(id) | 2,898 (2,766~3,391) | 6,823 (5,988~6,823) |
| 비파티션 복합 PK | 3,896 (3,225~3,964) | 6,854 (6,790~6,954) |
| 파티션 | 4,826 (4,002~4,850) | 6,564 (5,174~8,073) |

**판정: 차이 없음.** 본 측정에서는 파티션이 66% 빨라 보였지만 순위가 실행 순서와 정확히 일치했고,
역순 대조군에서는 세 구성이 6,564~6,854 로 구분되지 않는다. 관측된 차이는 호스트 페이지 캐시
워밍이 만든 것이다.

기전은 단순하다. 인덱스 B-트리는 하강만으로 시작 위치를 찾으므로, 파티션이 나뉘어 있든 아니든
읽는 인덱스 엔트리 수와 행 수가 같다. **프루닝이 줄여 줄 것이 애초에 없다.**

### 실험 A' — 같은 조회, `ORDER BY id`

| 구성 | TPS | 평균 레이턴시 |
| --- | --- | --- |
| 비파티션 PK(id) | 0.8 (0.8~0.9) | 33.5초 |
| 비파티션 복합 PK | 1.0 (1.0~1.1) | 28.0초 |
| 파티션 | 6,520 (6,000~6,638) | 5.9ms |

**판정: 약 7,800배.** 정렬 기준만 바꿨는데 옵티마이저가 `idx_created_date` 레인지 스캔을 버리고
PK 순 인덱스 스캔 + 필터를 고른다. 데이터가 append 순서라 2024년 행은 id 6,666,669 부터 시작하므로,
비파티션 테이블은 앞선 667만 행을 훑고서야 첫 행을 만난다. 파티션 테이블은 `p2024` 안에서 시작한다.

이 격차는 워밍 밴드(최대 2.3배)를 세 자릿수 넘어서므로 순서 효과로 설명되지 않는다.
다만 이것은 **파티셔닝이 나쁜 실행 계획을 구제한 사례**이지, 파티셔닝의 일반적 이득이 아니다.
같은 문제는 인덱스나 힌트로도 해결된다.

### 실험 A'' — 한 해 전체 집계

```sql
SELECT COUNT(*), SUM(price), AVG(stock_quantity) FROM <table>
WHERE created_date BETWEEN '2024-01-01' AND '2024-12-31';
```

세 테이블 모두 풀스캔을 탄다. 비파티션은 993만 행, 파티션은 `p2024` 의 166만 행만 읽는다.

| 구성 | TPS | 평균 레이턴시 | 실패율 |
| --- | --- | --- | --- |
| 비파티션 PK(id) | 0.5 (0.4~0.6) | 51.3초 | 0% |
| 비파티션 복합 PK | 0.5 (0.4~0.6) | 54.0초 | 최대 22.6% |
| 파티션 | 4.8 (4.6~4.8) | 8.3초 | 0% |

**판정: 9.5배 이상.** 비파티션 복합 PK 는 k6 기본 요청 타임아웃(60초)에 걸려 31건 중 7건이 잘렸으므로,
실제 격차는 이보다 크다. 즉 9.5배는 하한값이다.

여기가 파티셔닝이 읽기에서 실제로 이득을 보는 지점이다. 인덱스로 시작 위치만 찾으면 되는 조회가
아니라, **구간 전체를 읽어야 하는 쿼리**여야 프루닝이 읽을 양을 줄인다.

### 실험 B — 파티션 키를 포함하지 않은 PK 점 조회

```sql
SELECT id, name, created_date FROM <table> WHERE id = ?;
```

파티션 테이블은 PK 가 `(id, created_date)` 라 `id` 만으로는 파티션을 좁히지 못하고
`p2020` 부터 `p_future` 까지 7개를 모두 뒤진다.

| 구성 | TPS | 평균 레이턴시 | 대조군 대비 |
| --- | --- | --- | --- |
| 비파티션 PK(id) | 6,706 (6,203~7,697) | 5.7ms | 기준 |
| 비파티션 복합 PK | 5,703 (5,692~6,166) | 6.7ms | -14.9% |
| 파티션 (7개 탐색) | 4,999 (4,918~5,327) | 7.7ms | **-25.5%** |

**판정: 25.5% 느려진다.** 방향은 예상대로지만 크기는 7배가 아니다. 존재하지 않는 파티션에 대한
인덱스 하강은 루트 페이지가 버퍼 풀에 상주해 값싸게 끝나기 때문이다.

이 실험은 순서 효과와 반대 방향이다. 실행 순서상 뒤에 돈 파티션 테이블이 오히려 느렸으므로,
25.5% 는 과소평가일지언정 과대평가는 아니다.

### 실험 C — JOIN 에서 댓글 테이블 프루닝

```sql
SELECT p.id, p.name, c.id, c.rating
FROM product_partitioned p JOIN comment c ON c.product_id = p.id
WHERE p.created_date BETWEEN ? AND ? AND p.id BETWEEN ? AND ?
  [AND c.created_date BETWEEN ? AND ?]   -- 이 줄만 있고 없고
ORDER BY p.id, c.id LIMIT 100;
```

두 쿼리는 조인 순서·접근 방식이 같고 **결과 집합도 100행으로 완전히 동일하다**(양방향 차집합 0).
다른 것은 댓글 테이블에서 뒤지는 파티션 수뿐이다 — 7개 대 1개.

| 구성 | TPS | 평균 레이턴시 |
| --- | --- | --- |
| 댓글 날짜 조건 없음 (7개 파티션) | 48.5 (37.7~50.5) | 814ms |
| 댓글 날짜 조건 포함 (1개 파티션) | 314.5 (159.5~321.2) | 125ms |

**판정: 6.5배.** 상품 1,000건마다 댓글 인덱스를 7번씩 뒤지느냐 1번 뒤지느냐의 차이다.

## 결과 — 쏠림 데이터셋 (2024 에 90%)

원본: [scripts/rebench/results/skewed/](./scripts/rebench/results/skewed/)

같은 실험을 2024년에 90% 가 몰린 데이터셋에서 반복한다. `p2024` 가 전체의 90% 를 담으므로
프루닝이 걸려도 읽을 양이 거의 줄지 않는다.

| 실험 | 균등 데이터셋 | 쏠림 데이터셋 |
| --- | --- | --- |
| A 범위 조회 | 차이 없음 | 차이 없음 (파티션 +36.8%, 순서 효과 범위) |
| A' `ORDER BY id` | 7,800배 | 563배 (16.9 → 9,511 TPS) |
| A'' 한 해 집계 | **9.5배** | **차이 없음** (0.7 → 0.7 TPS) |
| C JOIN 프루닝 | 6.5배 | 1.27배 (71.4 → 90.6 TPS) |

**집계에서 이득이 완전히 사라진다.** 균등 데이터셋에서 9.5배였던 차이가 쏠림에서는 8%(변동폭 안)다.
프루닝이 `p2024` 하나로 좁혀도 그 안에 900만 행이 있으니 읽을 양이 그대로다.

### 집계·JOIN 의 순서 효과 대조군

실험 A 에서 순서 효과가 결과를 통째로 뒤집었으므로, 집계와 JOIN 도 역순으로 다시 돌렸다.

| 케이스 | 본 측정 | 역순 대조군 |
| --- | --- | --- |
| JOIN — 댓글 조건 없음 (7개 파티션) | 71.4 TPS | 62.4 TPS |
| JOIN — 댓글 조건 포함 (1개 파티션) | 90.6 TPS | 80.8 TPS |
| JOIN 차이 | +26.8% | +29.5% |
| 집계 — 비파티션 PK(id) | 0.7 TPS | 0.6 TPS |
| 집계 — 비파티션 복합 PK | 0.6 TPS | 0.5 TPS |
| 집계 — 파티션 | 0.7 TPS | 0.7 TPS |

JOIN 은 순위와 격차가 양쪽에서 거의 같으므로 프루닝 효과가 실재한다. 집계는 양쪽 모두 0.5~0.7 TPS 로
구분되지 않아 "차이 없음" 이 확정된다. 두 쿼리 형태 모두 순서 민감도가 낮으므로, 같은 형태로 측정한
균등 데이터셋의 9.5배·6.5배도 순서 효과로 설명되지 않는다.

A' 의 격차가 7,800배에서 563배로 줄어든 것도 같은 이유다. 쏠림 데이터셋에서 2024년 행은
id 800,001 부터 시작하므로, 비파티션 테이블이 건너뛰어야 할 앞선 행이 667만에서 80만으로 준다.

## 종합

| 쿼리 형태 | 파티셔닝 효과 | 조건 |
| --- | --- | --- |
| 파티션 키로 필터 + 인덱스로 앞부분만 조회 | 없음 | 인덱스 B-트리가 이미 시작 위치를 찾는다 |
| 파티션 키로 필터 + 구간 전체 집계 | 파티션 크기 비율만큼 (균등 9.5배) | **데이터가 고르게 퍼져 있을 때만** |
| 옵티마이저가 PK 순 스캔을 고르는 조회 | 수백~수천 배 | 나쁜 계획을 구제한 것. 인덱스로도 해결 가능 |
| 파티션 키 없는 점 조회 | -25.5% | 파티션 수만큼 인덱스를 뒤진다 |
| JOIN 에서 조인 대상에 파티션 키 명시 | 6.5배 (쏠림에서는 1.27배) | 결과 집합이 같은 조건에서 |

읽기 성능만 놓고 보면 파티셔닝의 이득은 **"파티션 키로 구간 전체를 읽는 쿼리" 에 국한되고,
그마저도 데이터가 파티션에 고르게 퍼져 있어야 한다.** 파티셔닝을 도입하는 더 확실한 이유는
`DROP PARTITION` 으로 오래된 데이터를 상수 시간에 지우는 운영 이득이다.

## 이 측정의 한계

- 상품 1,000만 · 댓글 2,000만 · 버퍼 풀 2GB 규모다. 실험 B·C 는 추가 인덱스 하강이 버퍼 풀에
  안 잡힐수록 격차가 커지므로, 더 큰 데이터에서는 파티션 탐색 페널티가 25.5% 보다 커질 수 있다.
- 앱·부하 생성기·DB 가 같은 로컬 머신에서 CPU 를 나눠 쓴다. 절대 TPS 는 환경 의존적이고,
  비교군 사이의 비율만 의미가 있다.
- 순서 대조군은 실험 A(균등)와 A''·C(쏠림)에서 돌렸다. 균등 데이터셋의 A''·C 는 직접 대조군을
  돌리지 않았고, 같은 쿼리 형태가 쏠림에서 순서 민감도가 낮았다는 근거로 판정했다.
- 반복은 3회다. 변동폭이 20% 에 달하는 케이스가 있어, 그 이하의 차이는 판정하지 않았다.
