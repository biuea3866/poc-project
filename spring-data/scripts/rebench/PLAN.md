# MySQL 파티셔닝 재검증 계획

기존 `mysql-partition.md` 결과의 결함 6건을 제거하고 다시 측정한다.

## 기존 결함과 대응

| # | 기존 결함 | 대응 |
|---|---|---|
| 1 | 댓글 실제 적재량(160만)과 문서 서술(2,000만) 불일치 | 실제 적재 행 수를 측정해 기록 |
| 2 | "2024년 집중" 서술이 시드 스크립트(2020~2025 균등)와 모순 | 균등·쏠림 두 데이터셋을 각각 시드해 분리 측정 |
| 3 | `product`에만 `idx_created_date` 존재 → 파티셔닝 단독 효과가 아님 | 두 테이블 인덱스 구조 동일화 + 동일 데이터 복제 |
| 4 | API3/4가 JOIN이 아닌 쿼리 2회, 결과 집합도 상이 | 실제 SQL JOIN으로 교체 + 결과 집합 동일성 사전 검증 |
| 5 | 1회 측정, 워밍업·버퍼풀 초기화 없음, 임계값 위반(포화) | 실행마다 MySQL 재기동 → 고정 워밍업 → 3회 반복, 중앙값 사용 |
| 6 | EXPLAIN 미기록, 원본 결과 JSON 미보존 | 전 쿼리 EXPLAIN 기록 + k6 원본 JSON 보존 |

## 실험 설계

데이터셋 2종을 별도 스키마로 시드한다. 두 상품 테이블은 **완전히 동일한 행**을 담는다(비파티션 테이블에서 복제).

| 데이터셋 | 상품 분포 | 목적 |
|---|---|---|
| `partition_uniform` | 2020~2025 균등 | 프루닝이 실제로 범위를 좁히는 경우 |
| `partition_skewed` | 2024에 90% 집중 | 쏠림 시 프루닝 이득이 줄어드는지 검증 |

댓글의 `created_date`는 **해당 상품과 같은 해**로 시드한다. 이래야 JOIN에서 댓글 날짜 조건이
결과를 바꾸지 않으면서 프루닝만 켜고 끌 수 있다 (실험 C의 전제).

| 실험 | A안 | B안 | 통제 변수 | 검증하는 주장 |
|---|---|---|---|---|
| A | `product` 범위 조회 | `product_partitioned` 범위 조회 | 인덱스·데이터 동일 | 파티셔닝 단독 효과 |
| B | `product` category 조회 | `product_partitioned` category 조회 | 파티션 키 미포함 | 키 없으면 파티션 수만큼 인덱스 조회가 늘어 느려진다 |
| C | JOIN, 댓글 날짜 조건 없음 | JOIN, 댓글 날짜 조건 포함 | 결과 집합 동일 | JOIN에서 프루닝 유무의 효과 |

각 실험을 두 데이터셋에서 반복한다.

## 측정 절차 (실행 1회 단위)

1. MySQL 컨테이너 재기동 → 버퍼 풀 초기화
2. healthcheck 통과 대기
3. 워밍업: 대상 엔드포인트에 5 VU로 30초
4. 측정: 기존과 동일한 부하 프로파일(30s ramp → 60s steady → 30s down)
5. k6 원본 JSON 보존

엔드포인트당 3회 반복하고 중앙값을 기록한다.

## 성공 기준

- 실험 A/B/C 각각에서 통제 변수 외 차이가 없음을 EXPLAIN과 행 수로 입증한다.
- 실험 C의 두 API가 **동일한 결과 집합**을 반환함을 SQL로 사전 검증한다.
- 3회 반복의 변동폭(min~max)을 함께 기록한다. 변동폭이 두 안의 차이보다 크면 "차이 없음"으로 판정한다.
